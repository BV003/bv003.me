## Speculative Decoding

### 建模

模型做一次前向，输入 n 个 token，会输出 n 个概率分布。
第 i 个分布是在已有前 i 个 token 的条件下，第 i+1 个 token 在整个词表上的概率。

所以只要把一串 token 一起喂给大模型，一次前向就能拿到每个位置的分布，这是并行验证的基础。

### 核心思想

先让小模型（draft model）自回归地快速猜 γ 个 token，记它在每个位置的分布为 q。
再把这 γ 个 token 一起输入大模型（target model），一次前向得到每个位置的分布 p。

从左到右逐个检查猜测的 token x：

- 如果 p(x) ≥ q(x)，直接接受
- 否则以 p(x)/q(x) 的概率接受

遇到第一个被拒绝的位置就停下，从 norm(max(0, p − q)) 重新采样一个 token。
如果 γ 个全部被接受，再从大模型最后一个位置的分布里多采一个。
所以每轮大模型前向会产出 1 到 γ+1 个 token。

可以从理论上证明，在这个验证规则下，投机解码的输出分布和只用大模型采样的分布完全一致。
直观上看：被接受的部分对应 min(p, q)，被拒绝后从 max(0, p − q) 补采的部分正好补上剩下的概率，两者加起来就是 p。

### 期望加速比

先定义几个量：

- α：接受率，也就是小模型猜的 token 被接受的平均概率
- γ：每轮小模型猜的 token 数
- c：小模型跑一次和大模型跑一次的耗时之比

接受率：

$$
\alpha = \mathbb{E}\left[\, \sum_{x} \min\big(p(x),\, q(x)\big) \right]
$$

每轮期望产出的 token 数：

$$
\mathbb{E}[\#\text{tokens}] = \frac{1 - \alpha^{\gamma+1}}{1 - \alpha}
$$

每轮耗时（以大模型一次前向为单位）：

$$
\text{Cost} = \gamma c + 1
$$

两者相除就是期望加速比：

$$
\text{Speedup} = \frac{1 - \alpha^{\gamma+1}}{(1 - \alpha)(\gamma c + 1)}
$$

这里有一个隐含前提：大模型一次前向验证 γ+1 个位置，耗时和只算一个位置差不多。
这在 batch 很小、瓶颈是显存带宽时成立，后面几篇论文都会围绕这个前提展开。

### 观察

投机解码本质上是多花计算来换时间：小模型要额外计算，大模型每轮也要多验证几个位置。

batch size 是同时处理的请求数。
大模型里绝大部分计算是矩阵乘法：输入向量 × 权重矩阵。
有 64 个请求时，把 64 个请求当前的 token 向量一行一行叠起来，和同一个权重矩阵相乘，权重只需要从显存搬一次。

每层 Transformer 由 QKV 投影、Attention、输出投影、FFN（MoE 模型里是专家）组成。
所有层算完以后，最后过一次 LM head，得到词表上的分布。
模型的各层按顺序计算，先算完前面的层，再算后面的层。
权重可以按层分块搬运，一边搬下一层的权重，一边算当前层。

一步前向要算 n 个 token（n = batch 里所有请求送进来的 token 总数），耗时是：

$$
T(n) = \max\big(\underbrace{T_{\text{mem}}}_{\text{搬权重，固定}},\ \underbrace{n \cdot t}_{\text{做计算}}\big)
$$

n 小的时候，耗时由搬权重决定，基本是常数，多算几个 token 几乎不花时间。
n 超过某个拐点以后，计算变成瓶颈，耗时随 n 线性增长。
打个比方：假设一步里的 token 少于 300 个时，耗时固定在 42 ms 左右；超过 300 个以后，耗时才开始随 token 数增长。具体拐点取决于模型大小和 GPU 型号。

所以投机解码的加速只在 n 小、也就是 batch 小的时候成立。batch 变大后，验证多出来的位置不再免费。

## EAGLE

作者认为，在特征层（倒数第二层的隐藏状态，就是 LM head 前面的那个向量）做自回归，比直接在 token 层猜更容易。

但特征有不确定性。位置的对应关系是：

tᵢ 输入大模型 → 得到 fᵢ → fᵢ 过 LM head 得到分布，采样出 tᵢ₊₁ → tᵢ₊₁ 输入大模型 → 得到 fᵢ₊₁

fᵢ₊₁ 取决于采到的是哪个 tᵢ₊₁，而只看 fᵢ 不知道采到了哪个。
所以要把 tᵢ₊₁ 和 fᵢ 一起输入，告诉 draft head 采样结果，这就是 token 序列要错开一位的原因。

### draft_head

EAGLE 草稿头的结构为拼接 [fᵢ ; e(tᵢ₊₁)] → FC 层（线性层，把拼接后的 2 倍维度压回原维度） → QKV 投影 → Attention → 输出投影 → FFN → 输出 f̂ᵢ₊₁。

看作一个黑盒，给一串前缀，猜下一个位置上大模型的特征会是什么。
输入是两条序列，分别是特征序列和 token 序列，token 全部往前错开一位。
输出是特征 f̂ᵢ₊₁，它只是一个向量；再过大模型冻结的 LM head，才得到下一个 token 的概率分布。

用大模型给一堆句子生成"标准答案特征"，然后像训练普通语言模型一样，让 draft_head 学会"给我 (fᵢ, tᵢ₊₁)，我输出 fᵢ₊₁"。
输出的特征和词都要对，再加一点噪声，防止它只会处理完美的输入。

### 树形预测

链的做法是每一步只取概率第 1 的词。树的做法是每一步取前几名，每个都往下接。

我们想让大模型只跑一次前向，就把树上所有节点都检查完。
把树拍平成一行，再用 tree attention mask 控制可见范围：每个节点只能看到前缀、自己的祖先和自己。

attention 部分加上掩码，做到一次前向，得到树上所有节点的概率分布。

验证时，同一个位置有多个候选。第一个候选被拒绝后，不是重新来：
先把 p 换成剩余分布 norm(max(0, p − q))，再用新的 p 去试第二个候选，依此类推。
有一个被接受，就沿着它往下验证子节点；这一层全部被拒绝，就从最后剩下的 p 里采一个 token，这一轮结束。
每次拒绝后减掉 q，是为了不重复计算已经试过的概率，这样输出分布仍然和大模型一致。

## Taming the Long-Tail（TLT）

这篇研究的是 RL 训练，不是推理服务。目标是缩短推理模型做 RL 训练的总时间。

### 背景：RL 训练的一步

以 GRPO 为例，每个 step 分两段：

- rollout：给模型一批题目，让它生成回答。这一段就是推理，一个 token 一个 token 地生成
- 训练：给回答打分，根据奖励更新模型参数

rollout 大约占每个 step 85% 的时间，所以加速 RL 训练主要就是加速 rollout。

### 长尾

推理模型的回答长短差别很大，大部分很早写完，少数非常长。
一个 step 要等所有回答都写完才能进入训练，所以耗时由最长的那几个回答决定。
越往后，还在生成的请求越少，batch 越来越小，先写完的 GPU 只能干等。
论文举的例子是 32B 模型在 128 张卡上训练 11 天只跑了 385 步，每步大约 40 分钟。

这正好是投机解码最划算的情况：batch 小，瓶颈在显存带宽，验证几个 token 和生成一个 token 耗时差不多，而且 GPU 本来就闲着。

### 直接用投机解码的困难

- 大模型每一步都在更新，事先训好的小模型会越来越不准
- EAGLE 这类小模型需要专门训练，有额外成本
- rollout 过程中 batch 一直在变小，最佳参数跟着变，固定一套不行

小模型过时不影响正确性，验证规则保证输出分布不变；影响的是速度。
接受率 α 取决于 q 和 p 有多接近。大模型一变，p 就变，旧小模型的 α 下降，加速就没了。
EAGLE 更严重：它的输入和要预测的目标都是大模型的特征，大模型参数一变，特征本身就变了。

### Adaptive Drafter：训练过程中顺手训练小模型

- 结构和 EAGLE 一样，一层 decoder，复用大模型的 embedding 和 LM head
- 训练数据不用额外造：rollout 时大模型做 prefill，把 hidden state 缓存下来，就是 EAGLE 要的特征
- 训练用空闲时间：协调器记录每个 worker 是忙、空闲还是在训练。长尾阶段空闲的 GPU 够多，就在上面训练小模型；rollout 结束就停，下次接着训
- 大约每 10 步训练一次，就能让小模型跟上大模型

### Adaptive Rollout Engine：按 batch 大小决定怎么猜

什么时候开：剩余请求数少于阈值（默认 32）才打开投机解码。batch 大时验证不再免费，开了不划算。

用什么参数：要选三个参数。

- 猜测深度：draft head 往后连续猜几步，相当于 γ
- topK：每个节点展开几个候选，决定树的宽度
- 验证多少个 token：从树上挑最有希望的若干个节点交给大模型验证

三个参数越大，能接受的 token 越多，验证的计算量也越大。
batch 小时验证几乎免费，大树划算；batch 大时计算成为瓶颈，小树或单链更好。

TLT 用 bandit 在线选参数。每组参数是一个选项，每次 decode 选一组去跑，记下这一步的速度。
大部分时候选目前平均最好的那组，偶尔试别的组。
不同 batch 下最优参数不同，所以按 batch size 分桶，每个桶单独统计、单独选。

### CUDA graph

不用 CUDA graph 时，每个 kernel 都要由 CPU 发射一次。一次前向有 K 个 kernel：

$$
T_{\text{step}} = K \cdot t_{\text{launch}} + \sum_i t_i
$$

用 CUDA graph 时，把这一串 kernel 录下来，之后整张图只发射一次：

$$
T_{\text{step}} \approx t_{\text{launch\_graph}} + \sum_i t_i
$$

长尾阶段 batch 小，Σ tᵢ 不大；投机解码又让 K 变大（draft head 跑 d 次、建树、采样、验证）。所以发射开销占比很高，CUDA graph 很重要。

代价是图里的形状和显存地址是写死的。batch size 或猜测参数一变，就要另一张图：

$$
\text{图的数量} = \text{batch size 的取值个数} \times \text{参数组合个数}
$$

每张图都要占显存，所以按 batch size 分桶，每个桶只录一套图。实际 batch 不够就补齐到桶的大小。
补齐多算的几行在小 batch 时几乎不花时间，因为 T(n) = max(T_mem, n·t) 在 n 小时是平的。
bandit 也只能在录好图的参数组合里挑。

### 结果

- 端到端训练比 VeRL 快 1.7 到 2.1 倍，奖励曲线重合，模型准确率不受影响
- 投机解码本身 bs=1 时 3.62 倍，bs=32 时 1.70 到 2.48 倍
- RL 训练后大模型反而更好猜，平均接受长度从 4.59 升到 6.53
- EAGLE 训练代价 1 倍、加速 2.24 倍；EAGLE-3 训练代价 7 倍、加速 2.55 倍，所以默认用 EAGLE

### 观察

TLT 找到了一个 batch 会自然变小的场景，只在这时打开投机解码，回到了第一篇"验证几乎免费"的前提。
小模型的训练成本藏进了本来就空闲的 GPU 时间里。
实验用了 64 张 H100，端到端结果很难复现，但长尾现象本身可以用小模型跑 rollout 观察。
如果异步 RL 或 partial rollout 把长尾本身消掉了，TLT 还剩多少收益，是一个开放问题。

## Performance or Illusion

在 vLLM 上把几类方法放在一起系统地测：n-gram、EAGLE、EAGLE-3、小模型、MTP。模型从 8B 到 70B 和 106B，任务有对话、摘要、数学、代码编辑，还有推理模型的数学和科学题，batch size 从 1 测到 128。指标用每秒生成的 token 数，因为不同设置下输出长度不完全一样，只看延迟不公平。

主要发现有五个。

第一，batch 越大，加速比越低。Llama3.1-8B 在 GSM8K 上用 EAGLE，bs=1 时 1.73 倍，bs=128 时只剩 1.21 倍。绝对吞吐还是随 batch 上升，但 speculative decoding 带来的相对收益在缩水。70B 降得更快，作者的解释是 4 卡并行时更早进入计算受限。

第二，时间主要花在大模型验证上，占 42% 到 95%，模型越大、batch 越大占比越高。猜测本身很便宜：n-gram 不到 2%，EAGLE 系列在 bs=1 时 12% 到 20%。小模型方法是例外，Qwen3-8B 配 0.6B 时猜测占到 47%，因为两者大小差得不够多。

第三，没有一种方法在所有任务上都最好。大多数任务上 EAGLE-3 或小模型最好，但代码编辑上 n-gram 最好，因为输出大量复制了输入里的代码。小模型方法好不好，关键不在接受率，而在小模型相对大模型有多贵：70B 和 8B 的接受率差不多，但小模型耗时占比分别约 12.5% 和 37.5%，所以 8B 上效果差。

第四，树状验证在大 batch 下反而变慢。bs=1 时树比单链好，1.85 倍对 1.65 倍。但树里大部分候选最后都被拒绝，单个候选的接受率从 0.415 掉到 0.095，大部分验证是白算的。到 bs=64，大树在所有任务上都比不开 speculative decoding 还慢，单链始终保持加速。

第五，接受率随位置下降。GLM-4.5-Air 的 MTP 按位置看，接受率从 0.92 掉到 0.68 再到 0.38。第一篇假设每个位置的接受率都是同一个 α，实际并不是。

### 结论

speculative decoding 不是没用，但收益强依赖场景：batch 大小、任务类型、小模型相对大模型的成本。作者认为值得做的方向是自适应，按 batch、按请求、按位置动态选方法和猜测长度。TLT 只在小 batch 时打开 speculative decoding，并用 bandit 调参，就是这个思路在 RL 训练里的一个实现。
